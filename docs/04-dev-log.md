# 开发日志

按时间顺序记录开发过程中的关键决策、真实踩到的坑与验证方式。日志只记录实际发生的事，不写"计划完成"。

## Day 1（10-03）：需求拆解与数据落地

- 通读赛题：技术向三问（解析统计 / 识别异常并给依据 / 漏报误报），方案要求两条（调研一种方法并说明理由、完成最小实验并输出一页报告），提交物要求四项（代码、使用说明、开发日志、日程记录、异常检测报告）。
- 拆成可验收的四件事：(1) 能解析真实日志并统计；(2) 能识别至少一类异常并给证据；(3) 能解释失效场景；(4) 仓库能一条命令复现。
- 用 Node 的 fetch 拉取 LogHub 官方 2k 样例（HDFS / Linux / Apache / Zookeeper 各 2000 行）与上游 README，落到 data/ 并记录来源 URL、字节数、解析出的时间范围。注：本机 pwsh 的 Invoke-WebRequest 报 TLS 失败，改用 fetch 下载成功。

## Day 1（10-03）：方法调研与选型

- 对比四类方法：模板挖掘/统计、不变量、深度学习、大模型。结论：主线用「模板挖掘 + 统计检验」，规则层做补充，理由写在 docs/01-method-research.md。
- 关键判断：2k 行量级无法训练序列模型；黑盒分数无法对应证据行；评委机器上不该要求 GPU 或第三方服务。
- 统计检验选择三层而不是一层：MAD 稳健 z（抗离群）、泊松上尾 + BH-FDR（给 p 值且控假阳性）、EWMA 控制图（对缓慢漂移敏感）。

## Day 2（10-04）：解析层与模板层

- 实现四种格式解析器 + 通用兜底 + auto 识别（头部采样命中率比较）。
- 自研 Drain：按 token 数分层、前 depth-1 个 token 建树、叶节点内序列相似度聚类、不一致位置替换为通配符；额外加掩码（blk_id / IP:Port / 数字 / 路径 / UUID / 十六进制）。
- 踩坑 1：Drain 的树路径依赖 token 字面量，若调用方忘记掩码，同一个模板会被分到不同叶子（"PacketResponder 7 for block blk_999" 与 "PacketResponder <NUM> for block <BLK>" 走不到一起）。定位后把掩码收敛到 Drain.add 内部，调用方只传原始正文。
- 踩坑 2：解析结果的行对象没有保留原始行字段，导致证据抽取时 KeyError: raw。修复：LogRecord.to_row 增加 raw，证据链从此可以回溯到行号。

## Day 3（10-05）：检测、融合与报告

- 实现 5 个检测器与融合层：同一模板被 z 与泊松同时命中只计一次；规则命中封顶；事件合并连续异常桶。
- 踩坑 3：ZooKeeper 解析器全量失配。原因是线程名里嵌套方括号（[QuorumPeer[myid=1]/...:FastLeaderElection@774]），原来的 [^\]]* 被第一个右括号截断。改为贪婪匹配后 2000/2000 行解析成功。
- 踩坑 4：Linux 样例有 8 行不匹配经典 syslog，两种写法：程序名带版本号（syslogd 1.4.1:）与 -- 前缀（combo  -- root[2421]:）。扩展正则后解析率 100%，四种数据集全部零兜底行。
- 踩坑 5：分数无上限。Linux 日志末尾一次"内核启动"带来 90 个新模板，加权后窗口分被推到 57.2，失去可读性。修复：新模板贡献按桶封顶 3.0，总分封顶 10.0。
- 自研绘图：本来计划用 matplotlib，但赛题约束是轻量，且容器里字体容易踩坑。改为 Canvas 抽象同时输出 SVG（GitHub 原生渲染）与 PNG（Pillow 可选降级），图表文字用英文避免位图字体缺字。

## Day 4（10-06）：基准评测、报告与复现验证

- 2k 样例没有标注，"检出 35 个窗口"无法证明准确。补注入式基准：注入 burst / novel / escalation 三类已知异常，按时间重叠判命中，算 P/R/F1 并做阈值扫描（docs/02 与 results/bench/bench_report.md 给出数字）。
- 踩坑 6：沙箱环境下 tempfile 不可用。TemporaryDirectory 清理时要 chmod，mkdtemp 以 0700 建目录，两者都被拒绝。改为在仓库内用普通 mkdir 建临时目录（build_tmp/），并加进 .gitignore。
- 补命令行自检：python -m loglens selftest 跑单元测试，全部通过（复核后新增 5 个产物契约用例，合计 50 个）。
- 补齐文档：数据集说明、方法调研、设计说明、一页异常报告、漏报误报分析、开发日志、日程记录；仓库初始化 git 并分阶段提交。
- 独立复核（由另一位复核者只读审查）：逐条核对了文档数字与产物、证据行与源日志、命令可运行性，发现并修掉三处"证据链/可复现性"问题：
  1) 统计口径：泊松检验的 BH-FDR 原先只对粗筛后的子集校正，家族大小不等于实际检验次数，FDR 保证被削弱；改为对全部检验（HDFS 样例为 284 次）做 BH，再用 alpha 做第二道门限。
  2) 证据可回溯：报告与 CSV 的证据行统一带上源文件行号（形如 L426 | 081110 ...），并逐行回查 data/ 确认命中。
  3) 复现命令：报告第 5 节改为"相对输入路径 + 真实输出目录"，照抄即可复现（此前写死了绝对路径与错误的输出目录）。
  另外把基准里 novel 注入行改成沿用目标数据集自身的头部格式（原先硬编码 HDFS 头，Linux/Apache/ZooKeeper 的注入行会格式混杂），并同步更新了所有引用到的数字。
- 复核后重跑全部实验与基准，文档数字与产物逐个自动比对，0 处不一致。
- 第二轮独立复核（同样只读、逐条自写脚本核对，覆盖 3612 条证据行、5 条命令可运行性、四数据集数字与基准数字）又发现两处实质问题与若干细节，已全部修复：
  1) 一页报告里样本 B 的统计量抄错了窗口（把另一条 T8/T7 记录的基线与 p 值拼到了 21:40 这条上）：改为该窗口真实值 观测 4 / 基线 0.335 / p=4.01e-04 / 11.9 倍；
  2) docs/03 §3.4 的每桶均量有 4 个数与产物口径不符：改为按「parsed.csv 按桶宽向下取整后对齐 windows.csv 桶网格，再按桶序号三等分」重算后的 4.6/8.0/13.7 与 9.8/6.0/10.1，并把口径写进正文；
  3) 细节：补上漏转的 Markdown 围栏、统一 0.5625 的取整口径、报告头部与数据概览也改用相对路径、README 的复现命令补上基准、Python 版本声明改为实测过的 3.10+、移除无效的 package-data 配置。

## 待办与已知不足

- 2k 样例时间跨度大（Linux 44 天 / 6 小时桶），桶内事件被平均，细粒度突发会变钝；用完整数据集时应把 target_buckets 调大或指定 --bucket。
- 规则表是针对常见故障语义手工维护的，换系统需要重新整理（已文档化为已知局限）。
- 有序序列异常（模板顺序错乱但计数正常）当前未覆盖，属于后续增强方向。
