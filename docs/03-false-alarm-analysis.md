# 漏报与误报分析

赛题第 3 问要求回答「你的方法在什么情况下会漏报或误报」。本文按「解析层 → 模板层 → 统计层 → 规则层 → 融合层」逐层给出失效机制、触发条件、在本实验数据上的具体表现，并说明已经做了哪些缓解、还建议做什么。文末附注入式基准的量化结果。

## 0 一句话结论

本方法擅长**「量变型」与「已知语义型」异常**：某类事件突然变多/变少、已知故障关键词出现、从未见过的新模板出现。
它**不擅长**三类问题：**没有日志的失败**（静默崩溃）、**计数正常的顺序异常**（模板顺序错乱）、**与正常业务波动同形的异常**（周期性任务、批处理窗口）。前者必然漏报，后两者需要引入序列模型或外部指标才能覆盖。

## 1 会漏报（false negative）的情况

| # | 场景 | 机制 | 触发条件 | 缓解措施 |
| --- | --- | --- | --- | --- |
| N1 | 异常只出现一两次 | 统计检验需要最小观测次数（min_observed=3）与显著性 | 偶发的致命错误（如单次块校验失败） | 降低 min_observed；对 ERROR/FATAL 级单条日志直接由规则层接住（本仓库已实现：级别规则命中 1 条即记录） |
| N2 | 静默失败 | 进程崩溃、节点失联时**根本写不出日志**，没有信号可分析 | 宕机、断电、内核 hang | 引入「日志心跳」反向指标：某来源在预期周期内没有日志 = 异常（本仓库尚未实现，属于下一步） |
| N3 | 模板漂移/分裂 | 同一事件因参数形态变化被聚成两个模板，计数被摊薄，谁都到不了阈值 | 版本升级、路径或主机名格式变化 | 定期复核模板表；对模板做合并/别名；监控「新模板生成速率」本身（novelty 已在做） |
| N4 | 时间桶过宽把突发摊平 | 桶宽由数据跨度自动决定（Linux 样例 44 天 → 6 小时桶），短促尖峰被平均 | 稀疏长周期日志 | 指定 --bucket 或用滑动窗口；完整数据集上把 target_buckets 调大 |
| N5 | 缓慢劣化但没有越限点 | EWMA 只对越限点报警，缓慢爬升的每一桶都还在控制限内 | 内存泄漏、连接数缓慢上涨 | 对 EWMA 的**斜率**报警（趋势检测），而不只是单点越限 |
| N6 | 计数不变的顺序异常 | 所有统计量都基于计数，A→B→C 与 C→B→A 完全同分布 | 依赖顺序错乱、状态机异常 | 引入模板序列模型（n-gram / 马尔可夫 / LSTM），本仓库未覆盖 |
| N7 | 规则表没覆盖的故障语义 | 规则是人工维护的白名单式先验 | 新组件、新错误类型 | 规则随复盘持续补充；用新模板检测兜底未知形态 |
| N8 | 异常持续时间过长被当作常态 | 中位数/MAD 与泊松基线都被异常"污染"，异常变成新基线 | 长期未恢复的故障 | 用更长历史或分时段基线；对"持续高位"单独设规则（例如连续 N 桶高于 P95） |
| N9 | 融合阈值过高 | 弱信号（规则/新模板/EWMA）权重低于 window_threshold，单独不成窗 | 只出现单一弱信号的故障 | 调低 --window-threshold（0.5 时召回从 0.844 升到 0.875，见第 3 节） |

**本实验中的真实表现**：注入的 burst（模板突增）灵敏度 1.000、novel（新错误模板）1.000、escalation（级别改写为 ERROR）0.625——量变型几乎不漏，语义型靠规则与新模板互补接住，级别抬升型最容易被漏掉（需要错误量控制图配合）。

## 2 会误报（false positive）的情况

| # | 场景 | 机制 | 数据里的表现 | 缓解措施 |
| --- | --- | --- | --- | --- |
| P1 | 正常业务突增 | 批处理、备份、扩容、促销都会让某模板计数飙升，统计上与故障同形 | HDFS 的块删除/复制高峰、Apache 的 jk2_init 高峰 | 引入同比/环比（上周同时间段）作为基线；维护「已知业务窗口」白名单 |
| P2 | 重启与升级 | 一批全新模板 + 量级跳变，同时触发新模板与 EWMA | 级别分布与来源分布同时变化 | 发布窗口抑制；把「新模板集中出现」与「发布事件」关联 |
| P3 | 上游抖动引起连锁重试 | 被调方故障，调用方刷重试，两边都报 | 跨组件的同步突增 | 关联多来源的时间相关性，做收敛（同一根因只报一次） |
| P4 | 日志轮转/采样/级别调整 | 采集侧变化导致量级跳变，与业务无关 | 单位时间日志量整体跳变 | 监控采集侧元数据；把"总量突变但模板分布不变"单独归类 |
| P5 | 周期性任务 | 每天/每周固定时刻的固定行为 | Linux 样例中每日 syslogd restart、cron 类事件 | 基于星期的周期性基线（seasonal 分解）；已知周期白名单 |
| P6 | 规则关键词过宽 | 正文里包含 error/failure 字样但并非故障 | Apache 的 "[client …] Directory index forbidden by rule" 属正常防护行为 | 规则加最小命中次数、加级别限定、加白名单反向规则 |
| P7 | 多重比较带来假阳性 | 成千上万次检验，按单次显著性水平必然会蒙对若干 | 本仓库对每个模板 × 每个桶都做检验 | 已实现 Benjamini-Hochberg FDR 控制（q=0.05），把"测得多"的假阳性压住；仍非零 |
| P8 | 小样本导致基线失真 | 2k 行样例里很多模板只出现几次，MAD=0 时退化为泊松尺度，敏感度偏高 | Linux/Apache 样例的 94/0 个单例与稀疏模板 | 设置 min_template_total（默认 4）过滤稀疏模板；报告里显式给出单例模板数量 |
| P9 | 桶宽过窄 | 桶越多、每桶计数越少，泊松尾检验越容易显著 | 2k 行样例的模板层单点判定达 215 条（HDFS） | 自动分桶把桶数控制在 60~400；用窗口阈值做二次过滤 |
| P10 | 全局流量水平漂移 | 业务自然增长、采集差异让"所有模板一起变多"，按绝对计数检验会把整段时间都标红 | 见第 3.4 节实测：HDFS 样例每桶均量从前 1/3 到后 1/3 增长约 3 倍，后段标红桶数是前段的 2 倍 | 按桶总量归一化后再比较「模板占比」，或引入同比基线 |
| P11 | 把"值得看一眼"当成"故障" | 工具输出的是候选异常窗口，不是确认的故障 | 干净日志上平均 24.75 个窗口 | 报告里区分严重度；生产环境配合告警聚合与人工反馈闭环 |

## 3 量化证据（注入式基准）

在没有人工标注的公开日志上，用可控注入自造真值：对每个数据集沿时间轴选 12 个互不重叠的窗口，分别注入 burst（某高频模板重复 18~45 行）、novel（3~8 行新错误模板）、escalation（窗口内最多 20 行改成 ERROR 级），匹配规则为「检测出的异常窗口与注入窗口时间重叠即命中」。4 个数据集 × 2 个随机种子 = 8 份注入日志、96 个注入窗口；每份日志用 6 种方法各评测一次，共 48 次方法评测。

### 3.1 窗口层面（融合后的异常窗口）

| 方法 | 精确率 P | 召回率 R | F1 |
| --- | ---: | ---: | ---: |
| 融合（默认配置） | 0.408 | **0.844** | **0.528** |
| 仅稳健 z-score | 0.382 | 0.688 | 0.464 |
| 仅规则 | **0.521** | 0.208 | 0.270 |
| 仅新模板 | 0.313 | 0.135 | 0.174 |
| 仅泊松 | 0.189 | 0.198 | 0.191 |
| 仅 EWMA | 0.046 | 0.021 | 0.029 |

### 3.2 单点层面（检测器灵敏度，消融实验）

融合层给弱信号设置了低于窗口阈值的权重，因此单看窗口会低估它们；下表统计单点判定是否落在注入窗口内。

| 方法 | 灵敏度 | burst | novel | escalation |
| --- | ---: | ---: | ---: | ---: |
| 融合（全部检测器） | **0.875** | 1.000 | **1.000** | 0.625 |
| 稳健 z-score | 0.688 | **1.000** | 0.563 | 0.500 |
| 规则 | 0.677 | 0.406 | **1.000** | 0.625 |
| 泊松 | 0.656 | 0.969 | 0.563 | 0.438 |
| EWMA | 0.240 | 0.219 | 0.344 | 0.156 |
| 新模板 | 0.156 | 0.125 | 0.156 | 0.188 |

**三点解读**

1. **稳健 z-score 是量变主力**：burst 灵敏度 100%，且无需标注与训练，印证主线选型。
2. **规则补语义短板**：规则对 novel 灵敏度 100%（注入文本含 IOException / DiskErrorException 等关键词），但在 burst 上只有 0.406；两条路线互补，融合后整体灵敏度 0.875。
3. **新模板检测的灵敏度天然偏低**：同一个新模板在时间轴上第二次出现时已不再是「新模板」（真值里有多个 novel 窗口复用了同样的注入文本），随后由计数类检验接管——这正是多层检测的意义。

### 3.3 阈值扫描与「噪声地板」

| window_threshold | P | R | F1 |
| --- | ---: | ---: | ---: |
| 0.5 | 0.357 | 0.875 | 0.493 |
| **1.0（默认）** | **0.408** | **0.844** | **0.528** |
| 1.5 | 0.348 | 0.646 | 0.440 |
| 2.0 | 0.345 | 0.458 | 0.384 |
| 3.0 | 0.286 | 0.281 | 0.276 |

**噪声地板**：不注入任何异常时，同一套检测器在原始日志上平均仍会给出 24.75 个窗口、277.75 条单点判定（HDFS 35 / Linux 42 / Apache 14 / Zookeeper 8 个窗口）。这些**不是纯粹的误报**——真实日志本来就有值得关注的波动与故障痕迹；但它说明：窗口层面的 precision 偏低主要来自「真实数据本身就有异常候选」，而不是检测器乱报。对生产环境而言，正确做法不是硬抬阈值，而是配套告警聚合、抑制规则与人工反馈闭环。

### 3.4 一个真实观察：非平稳流量会制造「看起来很多」的异常

把每个数据集的 2000 行按时间三等分，统计每桶平均日志量与被判红的桶数：

| 数据集 | 前 1/3 每桶均量 | 中 1/3 | 后 1/3 | 标红桶数（前 / 中 / 后） |
| --- | ---: | ---: | ---: | --- |
| HDFS_2k | 4.6 | 7.9 | 13.8 | 18 / 19 / 37 |
| Linux_2k | 7.0 | 15.2 | 12.4 | 20 / 29 / 24 |
| Apache_2k | 9.4 | 6.3 | 10.1 | 16 / 16 / 23 |

HDFS 样例后 1/3 时间段的日志密度约为前 1/3 的 **3 倍**，标红桶数也是前段的 2 倍。这说明：在这些
2k 行样例上，「异常窗口多」有一部分来自**流量水平本身的漂移**，而不是某类事件真的异常——按绝对计数
检验时，全局抬升会被读成「所有模板同时突增」。

**生产化时应改为比较「模板占该桶总量的比例」**（或先对每桶总量做归一化再检验），这样既能抓住
「某类事件相对变多」，又不会把整体流量增长误判为异常。本仓库保留绝对计数口径，是因为它对
「日志中断 / 骤降」这类场景更直观，且当前定位是候选窗口发现器而非告警器。

## 4 已实现的缓解措施

| 措施 | 作用 | 代码位置 |
| --- | --- | --- |
| Benjamini-Hochberg FDR 控制 | 抑制"检验次数多"带来的假阳性 | loglens/detectors/poisson.py |
| 同一模板多检测器去重 | 同一事件不被重复计数、不抬高分数 | loglens/detectors/ensemble.py |
| 信号分项封顶 + 总分封顶 | 防止某一类信号（如一次升级带来 90 个新模板）淹没其它证据 | loglens/detectors/base.py、ensemble.py |
| 最小观测次数 / 最小模板次数 | 过滤稀疏计数导致的噪声 | DetectConfig（min_observed、min_template_total） |
| 弱信号需相互印证 | 规则/新模板/EWMA 单独不成窗，降低误报 | window_threshold 默认 1.0 |
| 解析率与兜底行显式可见 | 解析失败不会被静默丢掉，避免"假阴性由解析造成" | loglens/parsers.py、报告第 1 节 |
| 原始日志行证据 | 每条告警可回溯到行号，人工复核成本低 | Anomaly.evidence / Incident.evidence |
| 阈值全部可调并写入 summary.json | 可按"宁可漏报/宁可误报"调整并复现 | loglens/cli.py、summary.json |

## 5 进一步建议（生产化方向）

1. **同比基线**：用上周同时间段替代全量中位数，消除周期性与业务增长带来的误报（针对 P1/P5）。
2. **日志心跳反指标**：为关键来源建立"预期出现频率"，低于阈值即报警（针对 N2 静默失败）。
3. **模板漂移跟踪**：监控模板新增速率与模板合并/分裂，识别版本升级与解析退化（针对 N3/P2）。
4. **趋势告警**：对 EWMA 序列做斜率检验，覆盖缓慢劣化（针对 N5）。
5. **多源关联收敛**：把同一时间窗内多个来源的异常合并成一个事件，减少连锁重试造成的重复告警（针对 P3）。
6. **人工反馈闭环**：让运维对告警标注"确认/误报"，用这些标签校准阈值并扩展规则表；积累到一定规模后可引入序列模型补顺序异常（针对 N6）。

## 6 适用边界声明

本方法定位是**候选异常窗口的发现器**，不是故障判定器。它把"看哪些日志"从 2000 行缩小到个位数窗口，并给出可复核的证据；是否构成故障、根因是什么，仍需结合业务语义与其它监控手段判断。
